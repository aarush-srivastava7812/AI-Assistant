# Building the Windows onboarding preview

The distribution bundles OpenCode for chat, the Python application backend and its CPU memory model. Setup installs a separate pinned Python/Hermes environment for advisory source tasks, and offers Docker Desktop installation. No user credentials, developer virtual environment, conversations or memory volume are packaged.

Public runtime pins are recorded in `desktop-app/resources/setup/runtime-manifest.json` and `opencode-manifest.json`. OpenCode 1.19.5 uses the official Windows x64 baseline release and its published archive SHA-256; its MIT license is included. The native task SDK is the unchanged official Hermes v0.22.5 source at commit `bf0203a794a07aac3ff764972ab9087baa4e4f4e`, installed with its frozen upstream dependency lock. Python 3.14.10 is installed privately without PATH or registry registration. The bootstrap's uv 0.13.6 executable is hash-pinned and ships its license notices.

For the staging scripts, acquire the exact upstream Hermes tag into `.local/hermes-native/source` and the verified uv executable into `.local/build-tools/bin/uv.exe`; the scripts reject a different commit, source modifications or bootstrap executable. `python desktop-app/scripts/stage-runtime.py` stages only Git-tracked upstream files. `python desktop-app/scripts/stage-opencode.py --download` acquires and verifies the public OpenCode archive and license. Generated executables and archives are ignored by Git and carried inside the release installers.

Use the project's qualified Python 3.12 build environment and locked `requirements/desktop-build.txt` for `desktop-app/scripts/freeze-backend.py`. Set `WAYFINDER_BUILD_MODEL_CACHE` to the complete public `models--qdrant--bge-small-en-v1.5-onnx-q` cache. A full freeze is required after backend inclusion-manifest changes. Then run `npm ci`, `npm run check`, `npm test`, and `npm run package` inside `desktop-app`. Packaging creates both the assisted NSIS Setup and the portable EXE.

`verify-onboarding.mjs` tests the packaged application through its own isolated windows and profile. A real connection test needs an explicitly authorized NVIDIA key supplied privately to the harness through `WAYFINDER_TEST_NVIDIA_KEY`; never put a key in command arguments or checked-in files. The harness removes that variable before launching the app and saves the key through the same Windows-encrypted main-process API as onboarding. `verify-portable.mjs` tests the outer portable launcher from an unrelated directory. `check-onboarding-package.mjs` pairs acceptance evidence to the exact archive and verifies the packaged source, model, manifests and runtime hashes.

Setup testing on an already configured laptop does not certify installation on a clean Windows VM. Docker license/UAC, virtualization/WSL enablement, reboot recovery and Google browser consent require separate interactive acceptance. The release verification record must retain those limits and must not label skipped paths as passed.
